# 季度统计功能实施方案（已确认）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task after the user approves the proposal. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** 增加季度评分趋势、季度评分对比、季度数量分布三项统计；固定日本、包含 NSFW、支持跨年起止季度，播放量暂缓。

**Architecture:** 首版直接对 PostgreSQL 的 Bangumi 主表进行聚合，不在浏览器下载全库，也不请求外站全库。FastAPI 提供趋势和单季度聚合接口，Next.js 新增统计页面，复用现有 SWR 与主题；统计范围独立于全站 NSFW 偏好。

**Tech Stack:** 现有 Python / FastAPI / SQLAlchemy / PostgreSQL、Next.js 14 / React 18 / TypeScript / Tailwind / SWR；建议增加按需引入的 Apache ECharts。

**Spec:** 用户于 2026-10-23 批准推荐方案，并明确：仅日本、包含 NSFW 且无开关，折线支持 2025 冬季至 2026 夏季等跨年范围。类型饼图按标签计次，评分为作品均分/当前最高分。仅返回汇总，不返回作品名称、ID、图片或详情链接。

## Global Constraints

- 已获授权实施前三项；不采集播放量、不变更现有作品数据，不执行数据同步。
- 首版以 Bangumi 主表为统计依据，外站详情补充缓存不参与聚合。
- 服务端固定 region=日本，包含 NSFW；接口不接收地区或 NSFW 筛选，响应只包含汇总。
- 评分为空与数量为零必须区分；无评分不能作为零分计入平均值。
- 多类型饼图的分母必须明确，不可将重叠作品数伪装成互斥的作品占比。
- 不将收藏人数、评分人数、平台热度标注为播放量。

## Review Focus

- 多类型与重复标签：同一作品在同一类型内只计一次，饼图分母遵循已确认口径。
- 未分类和来源“其他”：保留这些记录并报告覆盖率，不能静默剔除。
- 空季度、零评分、未来首播：数量返回零，无法计算的评分返回 null，趋势保留时间轴断点。
- 改变全站 NSFW 偏好不影响统计；请求不能切换到其他地区，汇总响应不泄露作品引用。
- 样本很少、跨年季度：样本数量可见，2025 冬至 2026 夏恰为连续七个季度，空季不断轴。

|---|---|

`score_details` 当前所有条目均有 1–10 分档的键，但未评分作品各档可以全部为零；评分人数可由各档求和，不能以字段非空代表有评分。`collects` 是上游各收藏状态人数的合计，不保存想看/在看/看过等状态的独立列，也不是播放次数。

现有 22 个类型：恋爱、搞笑、奇幻、科幻、异世界、日常、治愈、热血、悬疑、运动、音乐、百合、机战、战斗、校园、后宫、冒险、推理、历史、偶像、美食、惊悚。

来源为单值：原创、漫画改、小说改、游戏改、动画改、其他。现有“来源”表示作品改编来源；Bangumi/MAL/Kitsu/AniList 应称为数据平台，两者不能混用。

类型与来源来自既有标签映射规则：公共标签优先，用户标签需要达到使用人数阈值 10；不代表已经人工完整分类。“其他”包含无法识别或尚未明确的来源；地区缺失时当前代码默认日本，统计会继承这个既有数据限制。

其他存储：

- `episode`：章节名称、序号、类型、播出日期、时长、简介。
- `anime_relation`：前传、续集等条目关系；不同续作仍是独立作品条目。
- `anime_external_source`：MAL/Kitsu/AniList 外站 ID、匹配状态、标准化补充资料、各平台独立评分及量表、排名、投票人数（上游可提供时）、检查/过期/访问时间。当前每个平台各有 38 条缓存，成功匹配分别为 MAL 25、Kitsu 26、AniList 28；没有覆盖全库。
- 角色、声优与制作人员主要通过接口读取并缓存，未建立完整的本地人物关系库。
- 收藏、浏览记录、提醒和展示偏好主要保存在当前浏览器；服务器保存匿名 AI 会话、消息、来源与引用条目，以及检索向量。

当前没有播放量字段，没有每日/每季度评分历史表，也没有每部作品历史最高分记录。外站快照按作品和平台覆盖更新并会过期清理，不是评分历史。

## 二、需求与统计口径草案

### 1. 统计对象与时间

- “类型”指恋爱、奇幻等 `genres`；TV/剧场版等 `category` 沿用现有分类，首版不额外增加作品形式筛选。
- 按作品首播季度归类：冬 1–3 月、春 4–6 月、夏 7–9 月、秋 10–12 月。
- 跨季度长篇仅在首播季度计入一次；不是逐季重复计入所有仍在播作品。续作按独立条目计数。
- 固定日本，包含 NSFW，不提供地区和 NSFW 开关，也不改动全站偏好。
- 没有首播日期的作品不进入季度聚合，界面报告未纳入数量。
- 使用每部作品当前保存的评分。因此趋势表示“不同首播季度作品的当前评分对比”，不能表述为“历史上当季的评分变化”。

### 2. 评分指标

建议首版统一使用 Bangumi，避免外站覆盖程度随访问情况变化，导致统计结果产生偏差。

对季度 Q、类型或来源 G 中的有效评分作品集合 S：

- **综合评分（作品平均分，推荐）**：`sum(score_i) / count(S)`，每部作品权重相同。
- **最高评分**：`max(score_i)`，表示这一组作品当前评分中的最高值；提示框只显示汇总与样本数。
- 有效评分需满足 `0 < score <= 10`。未评分作品计入数量分布，但不进入评分指标。
- 按类型分组时，多类型作品进入每个相关类型，在各组内只计一次。
- 无有效评分时返回 null，显示“暂无评分”，折线不补零、不强行连接断点。
- 显示组内总作品数、有效评分作品数与评分人数；样本不足时给出提示，不静默改变样本范围。

“综合评分”也可以定义为按评分人数加权：`sum(score_i * votes_i) / sum(votes_i)`，现有分档数据支持计算，但结果更受热门作品影响。首版建议不额外增加这一指标开关，等待用户明确是否偏好加权定义。跨平台综合评分是另一种需求，当前覆盖率不足，不建议首版采用。

### 3. 数量与饼图

来源是单值，数量占比可直接按 `该来源作品数 / 当季作品总数` 计算，保留“其他”。

类型是多值，不能直接将每类作品数除以总作品数后画成饼图，因为比例之和可能大于 100%。有两种可行方案：

1. **按类型标签计次（推荐）**：一部“奇幻、恋爱”作品在两类各计一次，分母为当季所有类型计次数之和；没有类型的作品记一次“未分类”。标题明确写“类型标签占比”，提示框显示涉及作品数；页面另外显示去重作品总数。
2. **按作品等分权重**：一部作品有 k 个类型，每类贡献 `1/k`，未分类贡献 1。饼图总权重等于作品数，但类型份额可能为小数，需要明确这是折算份额，并单独显示实际涉及作品数。

不建议任意取第一个标签作为“主类型”，当前没有可靠的主类型字段。以上饼图选择不影响评分图各类型独立分组的口径。

### 4. 播放量评估

现有数据库和四个已接入的数据源适配器没有保存播放次数。官方字段说明中，Bangumi 提供评分/收藏，AniList 的 popularity 是加入清单的用户数，Kitsu 提供用户数/收藏数；这些都不能等同于视频播放量。

因此建议首版暂缓第 4 项。后续若限定到某个播放平台，再单独确认作品匹配、地区覆盖、访问方式，以及“全剧累计播放次数”或“季度内新增播放次数”等指标。后者还需要持续采样历史数据，不能用当前累计量直接推回过去。

如果用户希望增加现成的热度指标，可另选 `collects` 做收藏热度趋势，明确显示“收藏人数”，不自动替换原播放量需求。

## 三、方案选择

| 方案 | 做法 | 取舍 |
|---|---|---|
| A：直接聚合主表（已确认） | PostgreSQL 按季度和维度计算，前端只接收聚合结果 | 现有字段足够，更新与主库一致，无需新增业务表，适合当前约 3 万部规模 |
| B：预计算统计表 | worker 更新季度汇总，接口读取汇总 | 查询更轻，但增加汇总任务、回填与一致性维护；当前先没有必要 |

独立的评分历史表用于“还原某个时间点的评分”，与预计算性能优化不是一回事；首版三项需求按当前评分比较时不需要它。

## 四、页面与接口建议

新增 `/stats`，在桌面和移动导航增加“数据统计”。页面分两个视图，复用主题；范围固定为日本并包含 NSFW：

- **季度趋势**：选择开始季度、结束季度、类型/来源、综合评分/最高评分。横轴按年季排列，每个分组一条折线；类型较多时支持选择和隐藏，来源可以一次展示全部六类。默认近五年，可完整查看所选时间范围。
- **季度对比**：选择某年某季及类型/来源。评分柱状图切换综合评分/最高评分；同一季度和维度的数量饼图同时展示，评分开关不改变数量图的样本。

图表提示框包含季度、分组、指标值和样本数；提供明细表便于核对。保留加载、无数据、错误重试状态，手机图例和长时间轴可滚动。图表颜色在不同视图中保持稳定。

API：

- `GET /api/stats/meta`：返回日本作品的可用年份、缺失首播季度数量、总量与当前季度。

- `GET /api/stats/trends`：接收起止年份/季度、`dimension=genre|source`、固定日本并包含 NSFW，返回完整连续季度轴，以及每组的均分、最高分、作品数、有效评分数。
- `GET /api/stats/season`：接收年份/季度与相同的公共筛选，返回各组评分、数量、饼图分母和分布结果。
- 响应同时给出统计时间、实际纳入样本、缺失日期/类型/来源情况与统计口径。不返回任何具体作品信息。

SQL 为全量聚合，不复用分页搜索结果。复用现有年份季度索引，先测查询耗时；首版无需预计算表。SWR 缓存键包含所有筛选；仅在测量表明确有需要时增加 Redis 短缓存，并将所有筛选和口径版本纳入键。

## 六、已确认内容

1. “类型”按题材类型（恋爱/奇幻等）理解，首版不额外增加 TV/剧场版筛选。
2. “综合评分”采用同组作品 Bangumi 评分的算术平均值；“最高评分”取同组作品当前分数的最大值。

4. 以首播季度归类，仅日本、包含 NSFW，无对应开关；未知类型和来源不静默删除。
5. 首版实施前三项，播放量暂缓；收藏热度仅在用户明确需要时另加。
